# Plugin API v1.1 integration

New generated plugins explicitly declare `api_contract_version: "1.1.0"` in
both `manifest.json` and `ui.json`. `manifest_version: 1`, `schema_version: "v1"`,
the JSON-line wire major and the canonical `.utp`/v2 signing envelope remain
unchanged. The generated SDK range is `>=1.1.0,<1.2.0`. Plugin release numbers are
independent of the SDK contract.

Verify the host's API, SDK and runtime health in Plugin Manager's platform
information. New v1.1 plugins cannot run on an old v1.0 host. Limited legacy
compatibility is a host policy for shipped historical plugins and existing
installations; it is not a way to publish new v1.0 plugins. Test a migrated
interface before changing its declarations. The CI host revision in
[UPSTREAM.md](UPSTREAM.md) is reproducible source, not evidence that a published
host release already supports it.

## Theme-aware sandbox UI

The starter requests `plugin.theme` and listens for
`plugin-appearance-changed` from its parent frame. Both provide an appearance
snapshot containing `mode`, `tokens`, reduced-motion/high-contrast information
and current allowed keyboard shortcuts. Validate `event.source === parent` and
correlate request IDs. The starter applies only `--ui-*` tokens and switches its
native `color-scheme`; forms, controls and scrollbars follow live host changes.

Use semantic tokens such as `--ui-bg`, `--ui-surface`, `--ui-text`, `--ui-dim`,
`--ui-border`, `--ui-accent`, `--ui-on-accent` and `--ui-radius-control`.
Fallback values keep a disconnected preview usable. Keep phone controls at
least 44px and inputs at least 16px. An iframe cannot read the host DOM, cookies
or private services. Existing `plugin.run-action`, `plugin.save-settings` and
write-only `plugin.save-secret` remain permission checked.

## Shared native UI

Native modules require explicit `frontend.native` approval and a
`native_frontend` declaration in **both** manifest and UI documents. Bundle
entries and styles below `native/`, then export `activate(context)`.
The host exposes its shared Vue runtime as `context.vue`; do not bundle a
second Vue runtime or import private application modules.

`context.ui` includes `PageHeader`, `UiModal`, `AppIcon`, `AccountChip` and
`PasswordInput`. `context.host` provides action/settings helpers, owned plugin
navigation, themed `confirm`/`prompt`, appearance snapshots/subscriptions, search
and reminder providers, and permission-gated shortcut registration. Components
receive host page context, including `record_id` for detail routes; validate
ownership in the plugin backend before reading or changing records.

```javascript
export function activate(context) {
  const { h, defineComponent } = context.vue;
  context.registerComponent("hello", defineComponent({
    setup() {
      return () => h("section", { class: "my-greeting" }, [
        h(context.ui.PageHeader, { title: "My greeting" }),
        h("p", "A native page using the current host theme.")
      ]);
    }
  }));
  context.onCleanup(() => { /* dispose owned listeners and timers */ });
}
```

`UiModal` opens when mounted; render it conditionally and handle its `close`
event. Do not treat it as a `v-model` dialog. Use `PasswordInput` for credentials
and clear them after the explicit save action. Native authority does not imply
storage, network, data, administrator or placement authority. Test denied
grants, mount/unmount, account changes, update, disable and revocation.

## Sidebar and settings placement

Navigation and `settings_sections` can set a plain-text `group` and up to three
`folders`. Settings also accept `area`: `account`, `preferences` or
`administration`. Administration sections require `visibility.admin_only`.
Ordinary navigation permissions remain required.

Joining built-in headers needs additional explicit consent, scoped by area:

| Area | Additional permission |
| --- | --- |
| Main sidebar | `frontend.placement.sidebar` |
| Administration settings | `frontend.placement.settings.admin` |
| Account settings | `frontend.placement.settings.account` |
| Preferences | `frontend.placement.settings.preferences` |

Each grant covers the area's existing headers and subfolders. There is no
individual Games-subtree permission. Custom extension groups do not require
these built-in-placement grants. Without a grant, or after revocation, an owned
contribution falls back to Extensions. Placement never authorizes backend
operations. Use stable contribution IDs; reserved host IDs cannot be claimed.

## Keyboard shortcuts

Declare `frontend.shortcuts` in both capabilities and permissions. `ui.json`
can declare up to 64 shortcuts with a stable `id`, descriptive `label`, one to
four `keys`, and exactly one declared `page_id`, `route_id`, `action_id` or
`control`. A `search`/`create` control also requires a declared `when_route_id`.
For example, this partial UI contribution targets the starter's real action:

```json
{"shortcuts": [{"id": "greeting", "label": "Say hello", "keys": ["Alt+H"], "action_id": "greet"}]}
```

Native modules with both native and shortcut grants can call
`context.host.registerShortcut({ id, label, keys, group, paths }, callback)`.
Keep the returned cleanup function and unregister dynamically removed keys.
The host retains existing bindings when an extension conflicts; Preferences
shows the conflict and lets users disable or remap keys. Shortcuts pause while
typing or using dialogs. Sandbox pages receive only the allowed binding
snapshot and may forward a declared shortcut ID through `plugin.host-shortcut`;
they cannot request arbitrary host paths.

## Host-managed tasks

Request `tasks.background` explicitly and declare a bounded `scheduled_tasks`
array in the manifest. Each task references a real, non-confirmed action in
`ui.json`. This partial manifest schedules the starter greeting for demonstration:

```json
{"scheduled_tasks": [{"id": "greeting", "name": "Greeting", "action_id": "greet", "min_interval_minutes": 5, "default_interval_minutes": 60, "max_interval_minutes": 1440}]}
```

Schedules start off in Administration → Tasks and offer interval, enablement
and Run now controls. They run with the host background administrator identity
and live action permissions, not the person clicking Run now. Revocation,
disabled plugins and unavailable runtimes pause execution. Keep actions
bounded and return a small non-secret summary. Same-installation updates retain
the schedule; reinstalling with a new identity creates a separate schedule.

## Palette and style contributions

Declarative `themes` require `frontend.themes`; provide both light and dark
colors using the schema's named palette fields. Native CSS overrides additionally
require `frontend.native`, a packaged stylesheet and explicit critical-risk
approval. Scope overrides to the selected theme's
`data-plugin-theme="<plugin-id>:<theme-id>"` selector so other themes remain
usable. Test preview, selection, light/dark, phone/desktop, disabling and grant
revocation. Native CSS is privileged; it is not a permission-free global stylesheet.

## Installation and branch previews

Every push and PR runs checks and uploads **unsigned-dist**. Download the artifact,
extract it and use the host's direct package upload; explicit unsigned consent,
publisher checks and permission review remain active. Older catalogue release
selection pins the version and disables automatic updates until resumed.
Signed releases still use the developer's own key, registry and manual workflow.
Never modify a published archive or release history to update its contract.
